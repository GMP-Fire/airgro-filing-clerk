# Filing Clerk

Files document-of-record attachments from Gmail into Google Drive, nightly, on GitHub's servers. Your laptop is not involved and does not need to be on.

## Why this exists

The Cowork scheduled task of the same name has never filed a single document unattended, and it never could. It reached Drive through an MCP connector whose `create_file` accepts content only as an inline string — so every byte of every PDF had to be generated by a language model, one token at a time. A 90 KB bank statement is about 120,000 base64 characters, which does not fit in a single tool call. The 190 documents in `filed.jsonl` were all placed by hand in live sessions on 4 September 2026.

Here the bytes go **Gmail API → this process → Drive API** as a resumable upload. No model is in the path and there is no practical size limit.

## What it does

- Reads `filing-rules.json` from Drive (`3. Financial Insurance/_Filing Clerk/`) on every run. **That file stays the source of truth** — add a sender or change a destination there and this code does not change.
- Searches Gmail for each rule, downloads matching PDF attachments, and uploads them into the destination folder under the naming template in the rule.
- Appends a record per document to `filed.jsonl` in the same folder. The Gmail Steward reads that file to decide when a thread is safe to archive, so this keeps working exactly as it does now.
- Raises a Todoist Inbox item (label `agent`, with a `key:` line) when a destination folder is missing. Nothing else. No digests, no email.

## What it deliberately does not do

- **Never creates folders.** A missing destination is a question for you, not a guess. It raises an item and skips that rule.
- **Never opens a password-protected PDF.** Payslips, bank statements and Momentum documents are copied byte for byte, exactly as issued.
- **Never touches Outlook.** Rules marked `"mailbox": "outlook"` are skipped silently by design — Gmail credentials cannot reach `andrew@airgro.co.za`. Those still need a live session.
- **Never deletes or archives mail.** That is the Gmail Steward's job.
- **Never uploads twice.** Deduped on `messageId::filename`, and it checks the destination folder for the filename before writing, so documents already filed by hand are recorded rather than duplicated.

## Setup

You do this once, with the laptop open. After that it runs on its own.

### 1. Create an OAuth client

1. Go to <https://console.cloud.google.com/> and create a project (any name).
2. **APIs & Services → Library**: enable **Gmail API** and **Google Drive API**.
3. **APIs & Services → OAuth consent screen** (now branded **Google Auth Platform**, with Branding / Audience / Data Access / Clients tabs): under **Audience**, choose **External**.
4. **Still under Audience: click "Publish app" and confirm.** This matters more than it looks. An app left in **Testing** status issues refresh tokens that **expire after seven days** — the clerk would work for a week and then start failing with `invalid_grant` every night. Publishing to production removes that expiry. You do *not* need Google verification: an unverified production app is capped at 100 users, and you are one.
5. **Clients → Create client → Application type: Desktop app**. Download the JSON.

### 2. Mint a refresh token

Unpack the tarball first, then work inside a virtual environment. macOS ships a Homebrew Python that refuses system-wide `pip install` (PEP 668, `externally-managed-environment`) — a venv is the clean answer, and it keeps these four packages out of your system Python entirely.

```bash
cd ~/Downloads
tar -xzf airgro-filing-clerk.tar.gz
cd airgro-filing-clerk

python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

ls client_secret*.json ~/Downloads/client_secret*.json   # find the real filename
python auth_setup.py ~/Downloads/client_secret_<the real name>.json
```

`client_secret_XXXX.json` is a placeholder — the real file has a long numeric name. Tab-completion is your friend. The `.venv` folder is gitignored, so it never reaches the repo.

A browser opens. Because the app is published but unverified, Google shows **"Google hasn't verified this app"** — click **Advanced**, then **Go to (unsafe)**. That warning is aimed at strangers being phished by someone else's app; this is your own app, in your own project, asking for your own data. Approve, and it prints three values. Then delete the JSON from Downloads.

If it prints "No refresh token came back", you have authorised this app before. Remove it at <https://myaccount.google.com/permissions> and run the script again.

### 3. Add the secrets

Repo → **Settings → Secrets and variables → Actions → New repository secret**:

| Secret | Where it comes from |
| --- | --- |
| `GOOGLE_CLIENT_ID` | printed by `auth_setup.py` |
| `GOOGLE_CLIENT_SECRET` | printed by `auth_setup.py` |
| `GOOGLE_REFRESH_TOKEN` | printed by `auth_setup.py` |
| `TODOIST_TOKEN` | Todoist → Settings → Integrations → Developer |

### 4. Test before trusting it

Actions → **Filing Clerk** → **Run workflow**, tick **dry_run**. It lists what it would file and writes nothing. Read that list. Then run it again without dry_run and check Drive.

The six documents sitting unfiled since 4 September — five FNB statements and the Nedbank home loan quarterly — should be the first thing it picks up.

## Changing what gets filed

Edit `filing-rules.json` in Drive. Nothing here needs to change.

A rule looks like this:

```json
{
  "id": "fnb-gold-business",
  "from": "noreply@fnb.co.za",
  "subject_any": ["FNB Account Statement"],
  "dest": "04 Banking/FNB Gold Business Account",
  "name": "{date} FNB Gold Business Account Statement {n}.pdf"
}
```

`dest` is relative to `3. Financial Insurance`. Name tokens: `{date}` (from the subject line if it carries one, otherwise the email date), `{yyyy-mm}`, `{subject}`, `{n}` (trailing number on the attachment filename — this is what keeps five same-minute FNB statements distinct), `{ref}`, `{provider}`.

## Knobs

Set as workflow inputs on a manual run, or as `env` in the workflow file:

| Variable | Default | Meaning |
| --- | --- | --- |
| `LOOKBACK_DAYS` | 30 | How far back to search. Raise it for a one-off backfill. |
| `MAX_FILES_PER_RUN` | 40 | Stops a runaway first run. |
| `MAX_EXCEPTIONS` | 5 | Cap on Todoist items per run. |
| `DRY_RUN` | off | Report only, write nothing. |

## A note on the credentials

`GOOGLE_REFRESH_TOKEN` is a long-lived key to your Gmail and Drive. It lives in GitHub Secrets, which are encrypted and not readable back out of the UI, and it is never printed in workflow logs. Treat it like a password: do not commit it, paste it into a chat, or mail it to yourself.

The Drive scope is broad (`auth/drive`) because the clerk has to read `filing-rules.json` and write into folders it did not create; the narrower `drive.file` scope only sees files the app itself made, which will not work here. Gmail access is read-only.

If you ever want to cut it off: <https://myaccount.google.com/permissions>, remove the app. The Action then fails loudly on its next run.

## When it goes quiet

The Gmail Steward already watches `filed.jsonl` and raises a `steward/unfiled/<sender>` item when a document of record sits unfiled past the grace period. That is what caught the original failure, six runs in a row, and it will catch this one going quiet too. The Cowork Filing Clerk task should now be repointed at supervision rather than filing, or retired.
